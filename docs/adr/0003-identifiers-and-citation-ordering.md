# ADR 0003 — Identifiers, citation ordering and enum storage

- **Status:** Accepted
- **Date:** 2026-09-10
- **Fills gaps in:** spec §06, which names `section_no_sort` and the table columns
  but does not specify identifier types, the sort-key format, or how the
  constrained-vocabulary columns are stored.

## Context

Spec §06 explains why `section_no_sort` exists — "9" sorts after "10" as text and
legal citations are full of 2A, 14B and 21-A — but leaves the algorithm open. It
also lists column names without types, so three choices had to be made before the
first migration, all of them expensive to change afterwards.

## Decision

### 1. Corpus rows use `BIGINT` identities; accounts use `UUID`

`statutes`, `statute_parts`, `statute_sections`, `statute_links`, `kb_chunks`,
`section_explanations`, `ingest_runs` and `ask_logs` use `BIGINT GENERATED BY
DEFAULT AS IDENTITY`. `users` and `api_credentials` use `UUID` with
`gen_random_uuid()` (core PostgreSQL since 13, so no pgcrypto).

The reason is not aesthetic. Section ids are packed into the generation prompt as
citation identifiers, one per retrieved block, and are then parsed back out of the
model's answer by the validator. A 36-character UUID costs roughly 13 tokens
against a 4-digit integer's one, on every block of every question, and buys
nothing: the corpus is public data with no enumeration concern. Account ids, by
contrast, appear in tokens and would leak user counts if sequential.

### 2. `section_no_sort` is a fixed-width, byte-sortable key

`app/services/kb/section_numbers.py` splits a rendered number into digit and
letter runs, ignoring every other character, and emits each run at a fixed width
followed by a `|` terminator: numeric runs zero-padded to 6 digits, alphabetic
runs upper-cased and space-padded to 4 characters.

```
"9"    -> "000009|"
"10"   -> "000010|"
"2A"   -> "000002|A   |"
"21-A" -> "000021|A   |"
"45ZF" -> "000045|ZF  |"
```

Consequences that were chosen deliberately:

- **Separators carry no meaning.** "21A", "21-A" and "21 A" produce the same key,
  because portals render the same inserted provision all three ways.
- **The column is `COLLATE "C"`.** The ordering is then a property of the schema
  rather than of whatever `datcollate` the server was initialised with. On a glibc
  `en_US.utf8` database the locale ordering happens to agree with the byte
  ordering for this format; on an ICU collation, where padding and punctuation can
  be ignorable at the primary level, that agreement is not guaranteed.
- **Overflow raises rather than truncates.** A numeric run above 999999 or an
  alphabetic run longer than 4 characters raises `SectionNumberError`. Truncating
  "45ABCDE" to "45ABCD" would silently place a citation next to the wrong
  provision, which is the worst failure this product can have; failing the ingest
  is the cheaper error.

### 3. Constrained vocabularies are `VARCHAR` plus a `CHECK`, not native enums

`statutes.level`, `statute_parts.kind`, `statute_links.relation` and
`ingest_runs.status` are text columns with named check constraints, mirrored by
`StrEnum` classes in the models. Native PostgreSQL enums cannot have a value
removed and need `ALTER TYPE` gymnastics inside migrations; a check constraint is
dropped and recreated in one line, and downgrades stay trivial.

`tests/unit/test_models.py::test_check_constraints_list_exactly_their_enum_members`
parses each constraint and compares it to its enum, so adding a member without
updating the constraint fails a test instead of failing an insert in production.

## Consequences

- Citation ids stay short in prompts, and `GET /v1/sections/{id}` takes an
  integer.
- The sort key is 64 characters wide at most, which fits three segments — more
  than any real citation needs.
- Two section numbers that differ only in separators are indistinguishable to the
  ordering. If a future Act genuinely uses "21 A" and "21A" as *different*
  sections, this decision is wrong and the key needs a fourth segment type. No
  Indian central Act in Tiers 1–4 does.
- Mixed identifier types mean two id conventions in one schema. The boundary is
  simple enough to keep straight: corpus data is integer, people are UUID.
